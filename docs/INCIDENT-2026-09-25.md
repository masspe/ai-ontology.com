# Incident de sécurité du 2026-09-25 : dépôt distant infecté

Statut : **dépôt distant nettoyé le 2026-09-25 après-midi, suivi en cours** (voir §8).
Le dépôt distant `github.com/masspe/ai-ontology.com` a porté un malware sur 29
branches, dont `main`, du 2026-09-24 17:00 UTC au 2026-09-25 13:50 UTC. Le dépôt local
du poste de ms-azeemarshad est propre et contient l'historique légitime complet ; il a
servi de source pour la remise en état.

Ce document est destiné à l'équipe et, si besoin, au support GitHub. Il ne contient
que des faits vérifiables : journal public GitHub, reflogs de ce poste, analyse
statique des fichiers. Rien n'a été exécuté.

## 2. Qui a accédé, qui a poussé

- Deux comptes apparaissent dans l'historique public du dépôt : `ms-azeemarshad`
  (développeur) et `masspe` (propriétaire du dépôt).
- **Le pousseur est `masspe`.** Les 30 événements `PushEvent` du 24 sept. portent ce
  compte. Seul un détenteur de ses identifiants, d'un token ou d'une clé SSH de ce
  compte pouvait les émettre.
- **L'auteur affiché est `ms-azeemarshad`, mais c'est une contrefaçon.** Le commit
  infecté `dc68710d4fdbc0de8842ac2dd27109b9362f8c4a` est une réécriture du commit
  légitime `047b22b` : mêmes parents (`57b2e0b`, `166b5ba`), même message, même
  auteur, même committer, même date à la seconde (2026-09-23 16:49:41 +0200). Seul
  l'arbre de fichiers diffère. Le commit n'est pas signé. Le même procédé a été
  appliqué au dernier commit de chaque branche touchée.
- **29 branches sur 43 sont infectées**, plus `coverage-badges` (poussée par
  l'attaquant, puis écrasée par la CI). Branches intactes : `claude/rust-rag-graph-db-X17sA`,
  `docs/plan-leftovers` (poussée après l'attaque), `feat/storage-phase1` à `phase4`,
  `fix/ingest-idempotent-type-decls`, `fix/lenient-llm-json`, `fix/llm-truncation`,
  `fix/network-error-message`, `fix/properties-visible`, `fix/ui-reset-bulk-xlsx`,
  `test/hardening`.
- Le procédé est automatisé : un outil a parcouru les branches, réécrit le dernier
  commit de chacune et forcé le push, en moins de trois minutes.

### Comportement du chargeur (analyse statique)

1. Interroge des RPC Ethereum publics (`1rpc.io`, `eth.drpc.org`,
   `ethereum-rpc.publicnode.com`, `eth-mainnet.public.blastapi.io`, ou la variable
   `ETH_RPC_URL`) et l'indexeur `eth.blockscout.com` pour trouver la dernière
   transaction émise par le portefeuille `0xa322E5f3D311D3080e6f0121063e9aDC2490Ef1a`.
2. Décode l'adresse de destination de cette transaction : ses 8 premiers octets sont
   deux adresses IPv4. C'est ainsi que l'attaquant publie l'adresse de son serveur
   de commande sans nom de domaine (technique « EtherHiding »).
3. Télécharge `http://<ip1>:443/0x/cls` puis `http://<ip1>:443/0x/ls`, chiffrés par
   XOR (clés en dur `q4FZkxX{!h,Sr3=@` et `y-p_>d$0B&@^1aQk`), avec un User-Agent
   Chrome et un en-tête `Sec-V` portant le marqueur de campagne `9-9993-2`
   (`global['!']='9-9993-2'` en tête du script). Repli sur l'en-tête de réponse
   `X-Payload-B64`.
4. Exécute la première charge par `eval` dans le processus courant, puis relance les
   deux dans des processus `node -e` détachés, fenêtre cachée, sorties ignorées. Elles
   survivent à la fermeture de VS Code ou du serveur d'auth.
5. Les charges finales sont servies en direct par le serveur de l'attaquant et n'ont
   pas été récupérées. Cette famille livre habituellement un voleur d'identifiants
   (navigateurs, portefeuilles, tokens Git et npm, clés SSH) ou un accès distant.

Le premier étage seul n'écrit aucun fichier et n'exfiltre rien. Tout le dégât est dans
les étages téléchargés.

### Rapprochement

Le schéma exact (fausse police dans un dossier de fonts, tâche VS Code à l'ouverture,
serveur de commande résolu via une transaction Ethereum, en-tête `Sec-V`, README
« Blockchain Explorer ») correspond à une campagne documentée depuis 2025 qui vise
les développeurs par de faux entretiens d'embauche ou de faux tests techniques. La
victime clone un dépôt piégé, sa machine est infectée, ses tokens GitHub sont volés,
puis tous les dépôts où elle peut écrire sont réinfectés de la même manière. C'est
l'hypothèse la plus probable pour le compte ou le poste de `masspe`.

## 4. Ce qui n'est pas en cause

- **L'assistant de développement (Claude Code) de ce poste.** Il ne pousse qu'avec
  les identifiants de ms-azeemarshad, jamais avec ceux de masspe. Tous ses pushs sont
  dans le journal GitHub sous ms-azeemarshad, le dernier le 23 sept. 14:49 UTC. Le
  reflog du poste ne montre aucune opération le 24 sept. Le commit infecté n'est
  arrivé sur ce poste que par un fetch le 25 sept., marqué `forced-update`.
- **La CI GitHub.** Elle ne lance ni le serveur d'auth ni VS Code ; elle a seulement
  republié les badges depuis un arbre infecté. Le payload n'y a pas été exécuté.
- **Le poste de ms-azeemarshad.** Jamais de pull ni de checkout des branches
  infectées, pas de `.vscode/`, pas de `config.bat`, arbre de travail propre,
  aucun hook git non standard.

## 5. Exposition

- Toute personne ayant cloné ou tiré le dépôt depuis le 24 sept. 17:00 UTC, puis
  ouvert le dossier dans VS Code ou lancé `npm run dev`, est à considérer comme
  compromise.
- Le poste de `masspe` est à considérer comme compromis d'office, et tous ses autres
  dépôts sont à vérifier avec les mêmes indicateurs.

## 6. Indicateurs de compromission

- Fichiers : `.vscode/tasks.json` avec `runOn: folderOpen` exécutant un `.woff2` ;
  `fonts/fa-solid-900.woff2` commençant par `global['!']=` ; `config.bat` à la racine
  d'un dépôt ; `auth.js` de plus de 30 Ko.
- Processus : `node -e` orphelin, détaché, sans fenêtre.
- Réseau : requêtes vers les RPC Ethereum listés ci-dessus et vers `eth.blockscout.com`
  depuis un processus `node` ; requêtes HTTP vers un port 443 en clair avec un en-tête
  `Sec-V` ; chemins `/0x/cls` et `/0x/ls`.
- Git : commits non signés dont l'arbre diffère du commit local de même hash de
  message, date et parents ; pushs forcés en rafale sur toutes les branches.
- Portefeuille de commande : `0xa322E5f3D311D3080e6f0121063e9aDC2490Ef1a`.

## 7. Remise en état (dans cet ordre)

1. `masspe` : révoquer tous les tokens d'accès, clés SSH, applications OAuth et
   sessions ; changer le mot de passe ; activer la double authentification ; relire le
   journal de sécurité du compte ; examiner le poste (`config.bat`, processus `node -e`,
   extensions VS Code et paquets npm récents) ; vérifier ses autres dépôts.
2. `ms-azeemarshad` : même rotation par précaution, y compris le token stocké dans le
   gestionnaire d'identifiants Windows.
3. Seulement ensuite, depuis ce poste : pousser en force les branches locales propres
   sur `origin` ; activer la protection de branche sur `main` (pas de push forcé, pas
   de suppression, revue obligatoire) ; ajouter en CI un contrôle qui refuse tout
   fichier de police non binaire, toute tâche VS Code automatique et tout fichier
   source anormalement obscurci ; ajouter `.gitattributes` pour figer les fins de
   ligne.
4. Conserver le SHA `dc68710` (et les 29 autres têtes infectées) pour l'enquête ; ne
   pas les purger avant accord de l'équipe.

Jusqu'à l'étape 3 : ne pas faire `git pull`, ne pas fusionner ni checkout `origin/*`,
ne pas lancer `npm run dev`. L'historique propre est dans le dépôt local de ce poste
(`main` = 2636588 et antérieurs).
