Architecture cible · pour 500 000 concepts et plus

Le graphe, une fois qu'il vit dans Postgres

Schéma, index, et les règles de performance qui décident si une requête dure 8 ms ou 8 secondes. Chaque index cible ici remplace une structure écrite à la main dans ontology-graph ou ontology-index — la migration retire plus de code qu'elle n'en ajoute.

PostgreSQL 16 + pgvector ≥ 0.7 + pg_trgm ~500 K concepts · ~2,5 M relations sept structures RAM remplacées
Principe directeur

Trois tables au lieu d'une

La tentation est de traduire Concept en une seule table. C'est le premier piège, et il coûte cher précisément dans ton cas : un catalogue vivant. Trois raisons de découper.

Un vecteur de 768 dimensions pèse 3 Ko. Rangé dans concepts, il fait passer la table de ~150 Mo à ~1,7 Go. Chaque parcours séquentiel, chaque VACUUM, chaque mise à jour de ligne traîne ce poids — alors que 95 % des requêtes ne lisent jamais le vecteur.

Le stock et le prix changent toutes les heures. S'ils vivent dans concepts.properties, qui est indexé en GIN, chaque changement de stock réécrit la ligne et remue l'index GIN et invalide l'entrée HNSW du vecteur. Pour 500 K articles mis à jour quotidiennement, c'est le poste de coût numéro un.

D'où la séparation : concepts reste étroit et stable, concept_embeddings porte le poids, concept_metrics absorbe les écritures fréquentes. Bénéfice supplémentaire non négligeable : tu peux ré-embarquer tout le catalogue avec un nouveau modèle dans une seconde ligne par concept, puis basculer, sans interruption.

Schéma

Les tables

Le schéma d'ontologie — petit, chaud, gardé en RAM

Ces trois tables font quelques kilo-octets et sont lues à chaque écriture pour la validation. Elles restent en cache applicatif, invalidé au changement de schéma. C'est la seule chose qui doit rester en mémoire. 

-- Types de concepts, avec sous-typage et contraintes.
CREATE TABLE concept_types (
  name                text PRIMARY KEY,
  parent              text REFERENCES concept_types(name),
  description         text NOT NULL DEFAULT '',
  allowed_properties  text[],           -- NULL = monde ouvert
  required_properties text[] NOT NULL DEFAULT '{}',
  disjoint_with       text[] NOT NULL DEFAULT '{}'
);

-- Clôture transitive du sous-typage, matérialisée.
-- Le nombre de types est petit (dizaines) : la recalculer à chaque
-- changement de schéma coûte moins qu'une CTE récursive par requête.
CREATE TABLE concept_type_closure (
  type      text NOT NULL REFERENCES concept_types(name) ON DELETE CASCADE,
  ancestor  text NOT NULL REFERENCES concept_types(name) ON DELETE CASCADE,
  depth     int  NOT NULL,
  PRIMARY KEY (ancestor, type)     -- ordre voulu : filtre par ancêtre
);

CREATE TABLE relation_types (
  name        text PRIMARY KEY,
  domain      text NOT NULL REFERENCES concept_types(name),
  range       text NOT NULL REFERENCES concept_types(name),
  cardinality text NOT NULL DEFAULT 'many_to_many',
  symmetric   boolean NOT NULL DEFAULT false,
  transitive  boolean NOT NULL DEFAULT false,
  functional  boolean NOT NULL DEFAULT false,
  inverse_of  text REFERENCES relation_types(name),
  description text NOT NULL DEFAULT ''
);

Les entités

CREATE TABLE concepts (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  concept_type text NOT NULL REFERENCES concept_types(name),
  name         text NOT NULL,
  description  text NOT NULL DEFAULT '',
  properties   jsonb NOT NULL DEFAULT '{}',

  -- Index plein texte calculé par la base : jamais désynchronisé,
  -- contrairement à un index applicatif reconstruit au démarrage.
  search tsvector GENERATED ALWAYS AS (
    setweight(to_tsvector('french', name), 'A') ||
    setweight(to_tsvector('french', description), 'B')
  ) STORED,

  version    int NOT NULL DEFAULT 1,   -- concurrence optimiste
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  updated_by text
);

-- Les vecteurs vivent à part : gros, froids, remplaçables en bloc.
CREATE TABLE concept_embeddings (
  concept_id bigint NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  model      text   NOT NULL,        -- deux modèles peuvent coexister
  embedding  halfvec(768) NOT NULL,  -- halfvec : 2 octets/dim au lieu de 4
  computed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (model, concept_id)
);

-- Attributs volatils : écrits en continu, jamais indexés en GIN.
CREATE TABLE concept_metrics (
  concept_id bigint PRIMARY KEY REFERENCES concepts(id) ON DELETE CASCADE,
  metrics    jsonb NOT NULL DEFAULT '{}',   -- stock, prix, remise…
  updated_at timestamptz NOT NULL DEFAULT now()
) WITH (fillfactor = 70);        -- laisse la place aux MAJ HOT

CREATE TABLE relations (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  relation_type text NOT NULL REFERENCES relation_types(name),
  source_id     bigint NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  target_id     bigint NOT NULL REFERENCES concepts(id) ON DELETE CASCADE,
  weight        real NOT NULL DEFAULT 1.0,
  properties    jsonb NOT NULL DEFAULT '{}'
);

-- Le journal d'audit remplace le WAL maison, avec ce qui lui manquait :
-- un auteur et un horodatage.
CREATE TABLE audit_log (
  seq     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at      timestamptz NOT NULL DEFAULT now(),
  actor   text NOT NULL,
  kind    text NOT NULL,
  payload jsonb NOT NULL
);
Index

Neuf index, et ce que chacun remplace

C'est le cœur de la migration : chaque structure en mémoire du code actuel a un équivalent natif, souvent meilleur, et qui n'a pas besoin d'être reconstruit au démarrage.

IndexSert àRemplace
UNIQUE (concept_type, lower(name)) Résolution nom → id, et unicité d'identité name_index: DashMap<(String,String), ConceptId> — et l'unicité devient garantie par la base au lieu d'être maintenue à la main
GIN (search) Recherche plein texte pondérée L'index inversé TF-IDF de lexical.rs
GIN (name gin_trgm_ops) Recherche par sous-chaîne et tolérance aux fautes L'index trigrammes [char; 3] de graph.rs
HNSW (embedding halfvec_cosine_ops) Plus proches voisins approximatifs Le balayage cosinus plat de vector.rs
GIN (properties jsonb_path_ops) Filtres sur propriétés Rien — aujourd'hui c'est un parcours complet
(concept_type, id) Listage et pagination par type concepts_sorted: RwLock<BTreeSet> + l'index par label
(source_id, relation_type, target_id) INCLUDE (weight) Expansion sortante d'un saut out_edges et out_edges_typed
(target_id, relation_type, source_id) INCLUDE (weight) Expansion entrante d'un saut in_edges et in_edges_typed
UNIQUE (source_id, relation_type) partiel Contrainte functional (≤ 1 sortante) Une vérification Rust qui peut être contournée par un autre écrivain 
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS vector;

CREATE UNIQUE INDEX concepts_identity
  ON concepts (concept_type, lower(name));

CREATE INDEX concepts_search ON concepts USING gin (search);
CREATE INDEX concepts_name_trgm ON concepts USING gin (name gin_trgm_ops);
CREATE INDEX concepts_props ON concepts USING gin (properties jsonb_path_ops);
CREATE INDEX concepts_by_type ON concepts (concept_type, id);

-- Les deux index d'adjacence. Le INCLUDE rend l'expansion d'un saut
-- « index only » : aucun accès au tas, ce qui est LE facteur décisif.
CREATE INDEX rel_out ON relations (source_id, relation_type, target_id) INCLUDE (weight);
CREATE INDEX rel_in  ON relations (target_id, relation_type, source_id) INCLUDE (weight);

-- HNSW : m et ef_construction se paient à la construction, pas à la
-- lecture. À 500 K vecteurs, monter maintenance_work_mem d'abord.
SET maintenance_work_mem = '2GB';
CREATE INDEX emb_hnsw ON concept_embeddings
  USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Une contrainte functional par type concerné, émise quand l'utilisateur
-- coche la case dans l'éditeur de schéma.
CREATE UNIQUE INDEX rel_functional_belongs_to
  ON relations (source_id, relation_type)
  WHERE relation_type = 'belongsTo';
Chemin d'une question

Quel index sert à quelle étape

Performance

Les règles qui décident de tout

Jamais un seul ORDER BY fusionné

le piège n°1

La traduction naïve de la fusion actuelle est une seule requête qui trie sur la somme pondérée. Elle est catastrophique : l'expression doit être évaluée pour chaque ligne, donc ni le GIN ni le HNSW ne sont utilisables — parcours complet de 500 000 lignes et 500 000 calculs de distance. C'est la différence entre 8 ms et plusieurs secondes. 

-- FAUX : aucun index utilisable
SELECT id FROM concepts c JOIN concept_embeddings e ON …
ORDER BY 0.5 * ts_rank(c.search, q) + 0.5 * (1 - (e.embedding <=> $1))
LIMIT 8;

-- JUSTE : deux top-K menés par index, fusion ensuite
WITH lex AS (
  SELECT id, ts_rank(search, websearch_to_tsquery('french', $2)) AS s
  FROM concepts
  WHERE search @@ websearch_to_tsquery('french', $2)
  ORDER BY s DESC LIMIT $3          -- top_k × 4
), vec AS (
  SELECT concept_id AS id, 1 - (embedding <=> $1) AS s
  FROM concept_embeddings
  WHERE model = $4
  ORDER BY embedding <=> $1 LIMIT $3
)
SELECT id, s, 'lex' AS src FROM lex
UNION ALL SELECT id, s, 'vec' FROM vec;

La normalisation min-max et le plancher de pertinence (0.4 × meilleur score, exactement comme aujourd'hui) restent côté Rust : quelques dizaines de lignes à traiter, autant le faire là où le code existe déjà.

Le filtre par type se bat contre l'index HNSW

arbitrage

Un WHERE concept_type = 'Article' posé après une recherche HNSW dégrade le rappel : l'index parcourt son graphe de voisinage puis on jette des résultats, donc on peut finir avec trois candidats au lieu de trente. Trois parades, dans l'ordre où je les essaierais :

a. Sur-échantillonner — c'est déjà ce que fait le code (× 16 au lieu de × 4 dès qu'un filtre est présent). Gratuit, suffisant dans la plupart des cas.
b. hnsw.iterative_scan (pgvector 0.8) : la base continue de parcourir jusqu'à obtenir assez de lignes après filtrage.
c. Un index HNSW partiel par type majeur, si un type domine le catalogue.

La traversée bornée devient une CTE récursive

équivalence exacte

TraversalSpec se traduit terme à terme : max_depth par une colonne de profondeur, max_nodes par un LIMIT externe, relation_types et direction par le choix de l'index sondé, subsume_concept_types par une jointure sur la table de clôture. Et le UNION — pas UNION ALL — rejoue exactement le rôle de l'ensemble des nœuds visités du BFS actuel : il élimine les doublons, donc protège des cycles. 

WITH RECURSIVE reachable(id, depth) AS (
  SELECT unnest($1::bigint[]), 0
  UNION                                -- dédoublonne = ensemble visité
  SELECT r.target_id, x.depth + 1
  FROM reachable x
  JOIN relations r ON r.source_id = x.id      -- utilise rel_out
  WHERE x.depth < $2
    AND (cardinality($3::text[]) = 0 OR r.relation_type = ANY($3))
)
SELECT c.* FROM reachable x
JOIN concepts c ON c.id = x.id
JOIN concept_type_closure cl ON cl.type = c.concept_type
WHERE cl.ancestor = ANY($4)
LIMIT $5;                                -- max_nodes

Un LIMIT placé dans le terme récursif n'est pas honoré comme on l'imagine : il ne borne pas le total. D'où le plafond à l'extérieur, ce qui rend max_nodes approximatif en cours de parcours mais exact en sortie — même comportement observable qu'aujourd'hui.

Les embeddings se calculent une fois, à l'ingestion

bloquant à 500 K

C'est la raison technique qui condamne l'architecture actuelle bien avant la RAM : reindex_all() recalcule tous les vecteurs au démarrage. Avec un vrai modèle, c'est 500 000 appels d'API à chaque redémarrage. Persistés en base, ils ne sont jamais recalculés — et un changement de modèle devient une seconde ligne par concept, puis une bascule.

À l'import massif, grouper les appels (~100 textes par requête) et construire le HNSW après le chargement, pas pendant.

Import massif : COPY, pas INSERT

minutes vs heures
CREATE UNLOGGED TABLE staging_concepts (LIKE concepts INCLUDING DEFAULTS);
COPY staging_concepts (concept_type, name, description, properties) FROM STDIN;
-- validation Rust ici, sur la table de transit
INSERT INTO concepts (…) SELECT … FROM staging_concepts
  ON CONFLICT (concept_type, lower(name)) DO UPDATE SET …;

UNLOGGED sur la table de transit évite d'écrire deux fois dans le WAL Postgres. Pour un catalogue de 500 000 lignes, l'écart avec des INSERT ligne à ligne est de deux ordres de grandeur.

Un réplica de lecture sert tes deux contraintes d'un coup

2 pour 1

« D'autres gens doivent interroger le graphe » et « je veux de la haute disponibilité » se règlent avec le même mécanisme : une réplication en flux. Le réplica encaisse les requêtes analytiques et les outils décisionnels — ils ne peuvent donc plus ralentir le chemin d'écriture — et il est déjà le serveur de secours en cas de bascule. Ajoute la restauration à un instant précis (PITR) et la sauvegarde gérée est faite.

Le dimensionnement des vecteurs est ton plus gros levier mémoire

choix précoce

Pour 500 000 concepts : vector(1536) en float4 pèse 3 Go de données plus l'index ; halfvec(768) tombe à 0,75 Go. Le rappel d'un modèle à 768 dimensions est très proche pour de la recherche de catalogue. C'est une décision à prendre avant le premier import massif, parce que la reprendre signifie tout ré-embarquer.

Ne fais pas de N+1 sur le sous-graphe

piège classique

Le code actuel parcourt des DashMap : un accès par nœud coûte des nanosecondes. En base, le même schéma d'accès devient une requête par nœud — 50 allers-retours pour un sous-graphe de 50 nœuds. Il faut ramener nœuds et arêtes en une seule requête, ce qui change la forme du code de traversée, pas seulement son implémentation.

Frontières

Ce qui ne descend pas dans la base

Les types disjoints

Aucune contrainte SQL n'exprime « une instance de A ne peut pas partager son identité avec une instance de B ». Reste dans le chemin d'écriture Rust.

Les cardinalités

functional devient un index unique partiel. Le reste (un-à-plusieurs, plusieurs-à-plusieurs) demanderait des déclencheurs coûteux : garde la validation applicative.

Le cache de schéma

Types de concepts et de relations sont lus à chaque écriture. Quelques kilo-octets, très chauds : ils restent en RAM, invalidés au changement de schéma.

La fusion et le plancher

Normalisation min-max et seuil à 0,4 × le meilleur score : quelques dizaines de lignes. Rien à gagner à le faire en SQL, et c'est plus testable en Rust.

Un écart de comportement à surveiller. Le classement lexical change. Le code actuel calcule sqrt(tf / longueur) × ln((n − df + 0.5)/(df + 0.5) + 1) ; ts_rank n'utilise pas cette formule. Les résultats resteront pertinents mais leur ordre bougera. Avant de basculer, constitue un jeu de requêtes de référence avec leurs résultats attendus — c'est le seul moyen de distinguer « l'ordre a changé » de « la recherche est cassée ».

Multi-locataire

Où mettre la frontière entre clients

Trois options, par coût croissant de mise en œuvre et décroissant de coût d'exploitation.

ApprocheIsolationQuand
Une base par client Totale. Sauvegarde et restauration par client, aucune fuite possible. Jusqu'à quelques dizaines de clients. Le plus simple à raisonner, et la migration d'un client ne touche pas les autres.
Un schéma par client Forte. Un seul serveur, des search_path distincts. Compromis raisonnable : une instance à exploiter, des sauvegardes encore séparables.
Colonne tenant_id + RLS Logique, dépend de politiques correctes. Une erreur de politique est une fuite. Centaines de clients, ou inscription libre-service. Exige de faire figurer tenant_id en tête de chaque index composite.

Pour ton cas — quelques clients, dont un très gros — je commencerais par une base par client. Ça garde la porte ouverte : un gros client peut recevoir sa propre instance dimensionnée pour lui, sans que cela change la moindre ligne de code.

Les correspondances d'index et les constantes (plancher 0,4 ; pools × 4 et × 16 ; formule TF-IDF ; champs de TraversalSpec) sont relevées dans le code aux commits ec71462 / f313b93. Les chiffres de dimensionnement sont des estimations d'ordre de grandeur à confirmer par un banc d'essai sur 500 000 concepts synthétiques avant de figer le schéma.
